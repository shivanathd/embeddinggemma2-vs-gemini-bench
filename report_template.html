EmbeddingGemma 2 vs Gemini Embedding 2

Can a free model running on this Mac replace Google's cloud embedding API? We ran {{ ROWS|length }} tests across eight departments, from code search to Malayalam voice queries, with both models on identical inputs. EmbeddingGemma 2 is the open model running locally. Gemini Embedding 2 is the paid API.

For English text, code, photos and PDFs, you don't need the cloud. The local model wins or ties {{ wins.local + wins.tie }} of {{ ROWS|length }} tests, answers a query in {{ "%.0f"|format(L.text_p50_loc) }} ms against {{ "%.0f"|format(L.text_p50_cloud) }} ms, costs nothing per document and keeps every file on the machine.

Pay for Gemini Embedding 2 when any of these apply:

  • You search in Urdu, Arabic, Tamil or Malayalam (local is 9 to 18 points behind on those languages).
  • You match questions to written answers in finance or developer support (finance: {{ f3(T.fiqa.loc_768.ndcg10) }} local vs {{ f3(T.fiqa.cloud_768.ndcg10) }} cloud).
  • You search sound effects, or let people search photos by speaking Hindi or Arabic.
  • One index mixes photos and text, and you add the per-type calibration described below.

If you choose the cloud for text only, test Gemini Embedding 1 as well. The older model beat Gemini Embedding 2 on finance, legal and languages in our runs.

Whatever you pick, chunk long documents. A relevant passage in the middle of a 2,000-token document drops search quality by more than half for both models.

Skip embeddings entirely for judging resume fit (both models score close to a coin flip), and consider plain keyword search for near-duplicate detection, where it scores {{ f3(B.quora) }}.

Do we really need it?

Do we need embeddings at all?

For near-duplicate questions, keyword search scored {{ f3(B.quora) }} against 0.99 for both models, so start there. Everywhere else embeddings pay off: code search {{ f3(B.codesearch) }} → {{ f3(T.codesearch.loc_768.ndcg10) }}, claims to evidence {{ f3(B.scifact) }} → {{ f3(T.scifact.loc_768.ndcg10) }}, developer answers {{ f3(B.stackoverflow) }} → {{ f3(T.stackoverflow.loc_768.ndcg10) }}.

Do we need the cloud?

Only for the cases in the decision chart: under-served languages, finance and support answer search, sound effects and non-English speech. That is {{ wins.cloud }} of {{ ROWS|length }} tests. Everything else runs free on the laptop.

Do we need 3072 dimensions?

No. The cloud's 3072d adds at most 0.01 nDCG over 768d and quadruples storage. 256d loses about 2 points for either model.

Do we need the full local model?

Not for searching. The 270M text-only build gives identical query vectors, so index photos and audio once with the full 740M model, then query with the small one on any device.

Do we need a GPU?

Not for queries: the 4-bit build answers in about {{ "%.0f"|format(X.q4_cpu.cpu4_q4_p50_ms) }} ms on 4 CPU threads. A GPU matters for bulk indexing, especially images (about 4 per second here on PyTorch).

Do we need a vector database?

Not below about a million documents. Exact search over 1M vectors at 256d took {{ X.ann_scale['256d'].brute_force_ms_per_query }} ms per query on this CPU. Above that, an HNSW index answers in under a millisecond and found {{ pct(X.ann_scale.real['256d']['hnsw_recall@10']) }} of the exact top 10 on real vectors.

Do we need hybrid search?

Only for some corpora. Adding keyword search lifted legal and the local model's finance and medical scores, but lowered code and science search. Measure it on your data first.

Do we need to fine-tune?

For Malayalam, Urdu or Arabic speech, or a narrow domain like finance, fine-tuning the open model is the way to close the gap without paying per call. The weights are Apache 2.0.

Method and caveats

  1. Same inputs: both models embed exactly the same texts, images and audio, truncated at 16,000 characters. Each gets its documented task prompt: a text prefix for EmbeddingGemma 2, a task_type for Gemini.
  2. Large corpora are sampled: for FiQA, Quora and StackOverflow we kept every relevant document for 300 sampled queries and filled to 8,000 to 10,000 documents with random distractors (seeded). The keyword baseline reproduces the same samples.
  3. Statistics: per-query scores for both models, 2,000 paired bootstrap resamples, 95% interval. A gap counts as a win only if the interval excludes zero and the gap is at least 3 points.
  4. Contamination: these are public datasets, and either model may have seen them in training. That inflates absolute scores (SciFact is unusually high for both); the comparison between models is the useful part. Test on your own data before committing.
  5. Synthetic inputs: spoken queries come from macOS text-to-speech, and the five translations came from Gemini 3.5 Flash. Real accents and noise will be harder.
  6. Small samples: PDF pages (18 queries) and voice notes (73 clips) have no confidence interval. Treat them as directional.
  7. Similarity scoring: the cloud model scored 0.77 Spearman on STS-B with its SEMANTIC_SIMILARITY task type, lower than expected. We did not tune task types beyond the documented ones.
  8. Shared machine: load average went above 200 during the run, mostly from a browser and endpoint security software, so local throughput figures are a floor.

What this benchmark does not cover

  • Your own documents. Public datasets can be in either model's training data; a small labelled sample of your own content is the test that matters.
  • Noisy real-world audio such as phone calls or messaging-app voice notes. FLEURS is clean read speech.
  • Fine-tuning. The open model can be fine-tuned on your data; the cloud model cannot.
  • Cloud rate limits, error rates and multi-day stability. Our runs saw no failed requests, but we did not stress the quota.
  • A phone. CPU-only timings on this Mac stand in for on-device numbers.
  • Rerankers and chunking strategies beyond the long-document test.

Watching it run: the bench-watch mod

A Claude Code mod (a plugin that adds to Claude Code's own interface) showed the benchmark live while it ran: which suites were running, the newest line of each log, a local-vs-cloud scoreboard that filled in as results landed, system load, and the tool calls Claude was making. It also adds a one-line summary to the status line and a /bench command to reopen the pane.

How it works

Every 3 seconds the mod reads logs/*.log and results/*.json, lists running processes and reads the load average, then redraws the pane. A tool.call hook records each tool Claude runs. It never blocks a tool: its bookkeeping errors are swallowed.

Install

Copy the five bench-watch/ files below into a folder, then start Claude Code with claude --plugin-dir ./bench-watch. Check it with claude plugin validate ./bench-watch and claude plugin test ./bench-watch. Point the paths at your own benchmark folder.
